# Project Guide adopts AI-driven mode

**Accepted by:** Maxim Nikitin (stakeholder)
**Date:** 2026-11-15

## Problem Description

Q30 recorded the stakeholder's explicit request to turn Project Guide into an AI-driven project. The overview still recorded user-driven mode, selected on 2026-10-10.

1. The [original driving-mode decision](20261004-1852-ai-driven-mode.md) requires a decision when a project's mode changes.
2. The [AI-driven delegation decision](20261115-1809-ai-driven-mode-as-delegation.md), as clarified by [framework consistency](20261115-1921-framework-consistency-and-guardian.md), already defines the applicable mode. The proposal was to apply that model to this project, not redesign it.
3. The Coordinator checked lifecycle readiness: the existing skills support both modes, and driving mode is independent of collaboration mode. Its verdict was no concern.
4. The framework guardian reviewed the proposal for consistency with accepted decisions. Its verdict was no concern provided the existing goal, scope, role authority, stakeholder reservations, and parked Q15 were preserved. The accepted proposal preserves those boundaries.
5. The stakeholder's direct instruction selects the existing AI-driven model. No new acceptance was inferred for framework redesign, external sharing, or unrelated work. No dissenting opinions were recorded.

## Decision

1. **Driving mode:** Project Guide is now AI-driven. Update the overview's Collaboration section accordingly and link this decision.
2. **Delegation:** The AI runs the lifecycle and makes decisions not reserved for the stakeholder, using the existing framework, skills, and project-local roles. It reports each choice and its reason without requesting stakeholder permission at non-reserved phase-choice gates. Role expertise and the framework guardian's blocking authority remain in force.
3. **Stakeholder reservations:** Project direction and goals, scope changes, platform and technology, naming, milestone definitions and confirmation, irreversible or outward-facing actions, and anything else the stakeholder reserves remain with the stakeholder. Sharing outside the local workspace, including pushing changes, still requires authorization.
4. **Records and oversight:** Delegated AI decisions name the deciding role as `AI (<role>, delegated)`. Required expertise owners give their verdicts. The stakeholder may override AI decisions; an override is recorded as a new decision rather than rewriting an accepted record.
5. **Milestones:** Meeting a milestone's criteria makes it ready for a demo. It is reached only after the stakeholder confirms it following the demo. This switch creates no milestones and confirms none.
6. **Parked work and roster:** Q15 remains parked until the stakeholder reopens it. Collaboration mode remains unresolved, and the existing provisional roster remains unchanged.

## Explanation

1. This is a stakeholder-made decision, not an AI decision granting itself delegation. It resolves Q30's driving-mode resolution point.
2. Only the project's driving mode changes. Its goal, framework scope, accepted decisions, storage, and role definitions do not change.
3. Delegation changes who passes non-reserved choices, not the framework's required records, checks, expertise boundaries, or phase responsibilities. Q26's separate record-timing question is not resolved by this switch.
4. No skill redesign or installation is needed because the source and installed skills already support AI-driven mode.

## Consequences

1. Set the overview's Driving entry to AI-driven and link this decision.
2. Remove resolved Q30 from `open-issues.md`, retaining Q31 as the next unused ID. Keep other issues unchanged.
3. No executable task is needed: this project-level configuration change is applied while recording the decision.
4. Do not infer permission to commit, push, install skills, schedule work, or reopen Q15. Any later work follows the applicable delegation and stakeholder reservations.
