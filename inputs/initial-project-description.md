ok, in this session I would like to focus on a particular aspect. First I will explain, don't change anything. I would like to make a workflow framework - which can be used for running the research, designing systems, planning work. Such process should be accessible by multiple contributors. Each contributor has at least one role and each role carryies set of expertises / experiences / backgrounds. How I see the workflow: research starts with the goal, it sources requirements from input files. Such input files might be organized in some special way - we can define it later. So the first step - is initialization of the research. During this phase - it shapes a structure as well - generates all the necessary files like project description - goal definition, constraints, blockers and open questions. Such structure should be persistent and shared across all contributors - they must have access to it. For instance - it can be in the form of Git project. Or it can be in the form of Confluence / Wiki pages. Or google docs - any persistent layer supporting distributed shared access. Then Usually each research starts first with some global problems - then they are broken into smaller ones - with indication what kind of expertise is required in order to resolve these problems. Once such open questions / problems / blockers are resolved - they are turned into decision records. Important - there is a phase between identifying / registering the open question - and making a decision. And this phase is about doing the research of the problem, thinking, exchanging opinions - finding a solution. It also requires - collecting information. Then input information must be classified by the framework: opinion, expert opinion (based on required expertise), fact (just a truth from the reality). It may also be tagged and annotated by the bias factor - so PM is biased to deliver as quick as possible and as cheap as possible - meaning such intention might compromise the quality and security sometimes. Backend engineer might in opposite - over engineer for now real value - just because of self sense of perfect technical approach (subjectively). Such biases should be identified and mentioned once information is received from role-holders. Also - input information must be validated against already established truths / decisions / facts. It can be also compared against other input information. In such validations / comparisons - contradictions always must be spotted. Once contradiction is identified - it becomes a blocker / open question requiring expertise to be resolved. Opinions without expertise should be collected under problems they discuss for historical / audit reasons / traceability - but also as an input for expertise-holder to validate and address - either with the rejection or with adoptation / acceptance - always reasoned why. So then such problem become solved and becomes a decision record. Together with making the decision - we record such decision - there is a skill for it already. But also - we update all the necessary research documents capturing the latest understanding / status / knowledge. In the end - the dynamics of such a framework are - research / design starts with the problem description - it breaks into smaller problems - they are resolved - becoming known and solved - they open the door to the next layer of open questions / problems - they also become resolve. So it is like moving the fog of war - until the whole map of the research journey is explored and everything necessary for the implementation is described and resolved. Including risks, dependencies. Now - right it first as is to the file: problem-description.md and then we continue discussion.
